# MonkeyHub 性能优化实验方案

2026-09-20 · 讨论稿 · 代码基线 `26cadb140d1a5b35506d77c610a3efe87447a1d0`

本方案回答：在任务结果同样可用、保留条件同样完整的前提下，MonkeyHub 能否让设计者更早看到可继续修改的候选，并减少完成任务所需的总调用成本？

OCBA 处理另一层资源问题：已有一组候选时，如何把有限的重复评价预算分配给仍有比较价值的候选。它可能减少达到某一选择可靠度所需的评价次数，但不直接缩短单次模型生成、CAD 求解或界面加载。今天的实作重点放在 OCBA；本文件固定性能实验的比较口径，避免把输入压缩、少调用和真正提速混作同一结果。

## 1. 目前结果支持从哪里开始

| 方向 | 已测证据 | 本轮拟测的新增问题 |
| --- | --- | --- |
| 工具回合折叠，#32 | 已接通 `studio_request` 有界等待与候选读回；已知修改可利用返回结果继续观察 | 同一任务、同一模型下，少一次模型往返能否稳定缩短到可用候选的时间？ |
| 上下文选择，#170 | 34 实体修订实验中，带完整依赖保护的 graph、lexical、hybrid 消费输入分别下降约 49.1%、44.0%、43.4%；完整答案为 19/20、19/20、17/20，full 为 19/20。graph 和 hybrid 各发生一次关键遗漏 | lexical 的较小输入是否在真实修改中保持质量，并在计入检索、更新与补读成本后获益？ |
| Stage 交接，#185 | 两个配对中，最终任务输入下降 39.4% 与 59.7%，耗时分别增加 18.1% 与减少 30.1%；四臂均通过该墙体任务的既定检查 | 会话重启损失的缓存、摘要准备和后续重复读取，是否抵消历史缩短的收益？ |
| 唤醒分流，#204 | 合成只读分流中，28 次检查的主模型唤醒从 28 次变为 20 次；两臂均为 28/28 正确处置。期间存在其他调用负载 | 放到连续修改任务后，是否减少总成本且不延迟必要干预？ |
| Jev 分流，#205 | 适配与失败回退已实现，真实 Jev 组尚未测量 | 在已有确定性分流之上，Jev 的额外调用、校准与回退是否仍有净收益？ |

上述上下文与分流实验没有完成真实建筑修改。其调用时间受并发影响，不能用来宣布稳定提速。Stage 数据同时出现提速和变慢，说明总输入量本身不能解释使用速度。原始证据分别见 [revision-v2](../../probes/spatial-observation-v1/revision-v2.md)、[Stage 交接](../CONTEXT_COMPILATION.md#confirmed-stage-continuation-185)、[分流结果](../../labs/event_gating/results.md)。

优先做两项：**工具回合折叠；带完整依赖保护的 lexical 上下文选择**。前者直接改变串行往返，后者已有可复用比较与明确失败题。Stage 和唤醒分流随后进入同一口径；暂不增加模型路由、强制 Critic 或新的观测框架。

## 2. 固定任务与“完成”的含义

首次实验使用现有公开夹具，保持既有项目身份、单位、初始状态、保留要求和修改意图。每一臂从相同的保留工程恢复；每次重复使用新的隔离副本，不接续另一臂生成的候选。

| 任务 | 固定请求 | 必须通过的结果检查 |
| --- | --- | --- |
| T1 局部数值修改 | 将既有檐口高从 0.3 m 改为 0.5 m | 足迹、支承基准与其他字段保留；檐口 Z=0.6–1.1 m，底座 Z=0–0.6 m |
| T2 关联构件修改 | 底座高改为 0.8 m，檐口高改为 0.5 m | 原足迹、支承与参数绑定保留；檐口随基准升至 Z=0.8–1.3 m；一次完整候选 |
| T3 新增构件 | 添加既定 4 m × 3 m × 2.5 m 独立体块 | 尺寸正确，既有实体和所有未请求字段不变 |
| T4 Stage 后入口深化 | 在已确认体量外添加两段墙，保留居中的 1.0 m 全高开口 | 复用 Stage runner 的 25 项检查；原体量控制和绑定保留；不把占位体量认作工程墙体 |
| T5 证据选择压力题 | 复用 revision-v2 的 10 条 held-out 问题 | 完整上游、传播闭包、条件与对应图片保留；单列 lintel/screen/seal 等关键遗漏 |
| T6 连续事件分流 | 复用 6 类事件、14 个检查点的 dev/holdout 固定输入 | 必须唤醒的变化无漏报；旧来源拒绝；视觉判断不能被语义分类代替 |

T1–T3 来自 [benchmarks.json](../../tests/monkeymonitor/benchmarks.json)，T4 来自 [Stage runner](../../tests/monkeymonitor/run_stage_handoff_benchmark.py)，T5/T6 继续使用已有 lab。题目的明确尺寸服务于可比较的机制测量，不代表真实设计任务都应由使用者输入坐标。

“可用候选”必须同时满足：生成完成、正确来源读回、预定几何和保留检查通过、界面打开同一候选且可选择对象。聊天回复、提交成功或一个旧模型首次可见均不算完成。终点是可继续修改的未接受候选，不自动接受 Stage 或发行项目。T5、T6 只能报告正确证据或正确处置，不能产生“到可用候选”的成绩。

在机制筛选后，另用两个尚未参与调参的建筑修改任务做迁移验证：一个局部构件修改，一个跨构件关系修改。任务来源和期望保留条件由项目负责人固定，不把当前合成题的成功率外推为建筑质量。

## 3. 比较安排

每个实验只改变表内的一个因素。基线也是当前同一提交中的合法执行路径，不恢复过时实现，不绕开来源、保留条件或候选验证。

| 实验 | A | B | 首轮规模与边界 |
| --- | --- | --- | --- |
| E1 工具回合 | 明确的提交、查询完成、结果读回分步调用 | 当前有界提交／等待／读回，复用已返回事实 | T1–T3 × 2 个缓存层 × 2 次重复＝12 对、24 个任务执行 |
| E2 上下文选择 | full 结构化上下文 | revision-v2 的 guarded lexical；溢出或无法定位时回退 full | T5 的 10 题 × 2 个缓存层 × 2 次重复＝40 对、80 个 consumer 调用；先筛查证据质量，随后才在修改任务中接入 |
| E3 Stage 交接 | 继续现有 provider 会话 | 明确接受 Stage 后建立新会话 | 先复用 T4，短历史与六轮历史各做 AB、BA；共 4 对，准备回合另计 |
| E4 事件分流 | 每个检查点均唤醒主模型 | 既有确定性 gate | 复用 dev/holdout 各 14 点，各 2 次配对；共 4 个配对流、112 个检查点处置，不当作 112 个独立建筑任务 |
| E5 Jev 增量 | E4 的 B | 相同规则后，对符合条件的语义事件调用 Jev | 只有真实接口可用才测；在 dev 选阈值，冻结后测 holdout；不同时改主模型或 gate |

E1 分步臂只保留完成同一任务必要的读写，不刻意增加重复轮询、解释或无效工具调用。二者都只生成一次候选；“中间步骤每次编译”不应成为人为减慢基线的办法。若当前工具不能在同一权限与来源条件下提供这两种路径，先报告此限制，不能把不同版本的一次运行当 A/B。

E2 首轮只选 full 与 lexical，因为当前证据没有显示引入嵌入比 lexical 更有利。graph/hybrid 作为失败分析材料保留；新的选择方案应先解决相关遗漏，再占用真实调用预算。E3 的短/长历史是预设任务条件，实际历史长度、准备调用和缓存用量均需保留；两臂历史内容若不同，报告为配对但非完全相同历史的设计，不隐去这一残余差异。

首轮数量用于发现明显回归和估计波动，**不是功效分析，也不足以证实 p95 改善**。待确定有希望的机制，再预先冻结新增样本量与停止规则；建议在同一缓存层取得至少 100 个执行/臂、覆盖两个时段及未用于调参的任务，再讨论尾部延迟。增加样本应在查看新增结果前决定，不因某一臂暂时领先而提前收尾。

## 4. 配对、缓存与运行负载

1. **固定模型与设置。** 同一 provider、实际返回模型、CLI/SDK 版本、推理强度、输出限制、工具权限与超时；别名漂移单独分层。接口没有 seed 时明确记录，不把本地随机种子写成模型可复现承诺。Codex 接口若不能强制输出上限，记录真实输出，不声称上限已被执行。
2. **配对并随机分块。** 相同任务与来源组成一对；每个“任务 × 缓存层 × 时段”块内预先随机分配 AB/BA，保证平衡；A/B 尽量相邻执行。在保存的运行清单中记录顺序及随机种子，种子只控制调度。这样控制任务差异与时段漂移，不能消除不可观测的 provider 调度。[NIST 随机区组设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)
3. **分别报告冷缓存与热缓存。** 每臂都采用相同的首次请求协议及相同的预热协议；从 provider 原始 usage 核验实际缓存读取。新会话不等于冷缓存，旧会话也不保证缓存命中。无法主动隔离 provider 缓存时，不通过改写无关提示来“制造冷缓存”，按观测缓存状态分层并保留全部样本。
4. **热缓存预热计账。** 每臂先执行同等指定历史或请求以形成其自己的有效前缀；预热开销独立列出，同时给首次使用总成本及随后复用成本。Stage 导致的缓存损失属于 E3 的作用机制，不能通过只比较成功命中的 Stage 样本把它排除。缓存写入、读取含义遵循 [Claude 官方缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。
5. **控制可控负载。** 正式延迟测量期间不同时跑 CI、大型 CAD 回归或其他已知模型任务。启动预检后固定运行环境，记录其他活动；不擅自停止使用者的程序。无法取得安静窗口的样本保留为负载观察，不并入“受控提速”主结论。
6. **不得自动补跑覆盖失败。** 超时、取消、格式失败、错误候选、回退和重试都占用原样本；恢复执行另行关联原尝试。每臂采用同一超时与最大修正轮数。人工判断等待另列，不混进自动执行阶段。

## 5. 耗时拆分：从点击到正确候选

主时间轴为 `用户提交 → 候选完成并读回 → 同一候选可见且可交互`。另外记录聊天结束时刻，使“模型还在解释但候选已经可用”与“回复结束仍未打开模型”能够被分别识别。

| 部分 | 当前观测入口 | 计量规则 |
| --- | --- | --- |
| Hub 排队、启动与上下文准备 | `hub_turn`、`context_build`、实际 provider 派发边界 | 有起止点才拆分；没有排队边界则留在未归因时间，不根据 CPU 空闲猜测 |
| 模型首 token 等待（TTFT） | provider 真正提供的 `first_token_ms` 或流首 token 边界 | Hub `first_response` 只是首段回复到达，不自动称为 TTFT；传输缓冲可能包含在其中 |
| 模型生成及响应等待 | 真实模型请求开始/结束、可用的首 token 事件 | 首 token 到末 token 仍可能包括流传输；`duration_api_ms` 不能改名为纯推理。没有内部遥测就只报告请求往返 |
| 工具、查询、CAD、验证与读回 | `tool_call`、`api_request`、`geometry_build`、`validation`、`candidate_readback` 等 | 父工具区间包含 CAD 子区间，不能直接相加；返回正确来源后才算该阶段完成 |
| 前端下载、安装、投影、首次可见 | 现有 browser/preview 记录中的 `model_download`、`model_install`、`model_projection`、`first_visible` | 核对 run/candidate 身份；在隔离的 headless 浏览器验收，不借用户活动页面做实验 |
| 最终可操作与余留时间 | 原有预览浏览器验收及 `TurnTrace` 的未归因区间 | 已记录事件不等于交互可用；能选中对象才结束。缺此检查时只能报告后端候选延迟 |

复用 [UsageLog/TurnTrace](../../monkeymonitor/trace.py) 的区间覆盖计算。报告端到端墙钟、互不重叠的前台阶段及未归因时间；后台任务另列。端到端不等于所有 span 的时长之和。多工具并行时，少了工具秒数也未必缩短关键路径。

`first_candidate_ms` 需来自本回合真实生成并成功读回的新候选；已有输入候选或后来手工读回不能倒填为首次结果。跨进程时间若不能可靠对齐，保留各自区间与外部总墙钟，不强行拼成精确瀑布图。

## 6. 用量、净成本与缺失记录

逐次保留实际输入、缓存读取、缓存写入、普通未缓存输入、输出与可获得的 reasoning 子集，并记录全部辅助模型、检索、Critic、失败调用及恢复调用。主模型一次少发 2,000 token，但额外增加一次检索模型或 Critic，不自动计为节省。

使用 MonkeyMonitor 归一后的口径：总输入包含缓存子集；普通输入＝总输入−缓存读取−缓存写入。Claude 原始 `input_tokens` 与缓存字段的口径不同，先按现有 adapter 归一。输出中的 reasoning 是子集时不重复相加；图片 token 已含于 provider 用量时也不加第二次。字节数或 `bytes/4` 估计只用来解释上下文结构，不能代替账单 token。

净成本分别报告：

- 本次成功或失败尝试的全部 provider API 等价费用；使用对应模型、缓存桶与有日期的费率。
- 首次准备、索引构建、更新、观察、渲染、预热和阈值校准；共同准备对每个替代方案只记一次，不跨 split 重复累加。
- 每个成功任务的成本＝该臂全部尝试成本 / 成功任务数。零成功不提供一个有限的“成功均价”；失败臂成本照列。
- 实际收费与 API 等价估算分开。没有账单证据时实际收费为 unknown；本地计算耗时照列，未测电费/硬件成本不填零。

已有空间实验出现 Monitor 分模型事件缺失，因此先核对原始 provider 结果、原生日志和 Monitor 中的调用身份。可恢复记录标出来源，重复事件去重；无法恢复的用量保持 `null`。每个表同时列计划任务数、实际尝试数、完整 usage 数及缺失数。费用只覆盖已知调用时标注“已知费用下界”，不能发布全任务净节省百分比。整个失败尝试仍保留在成功率与超时率的分母。

provider 未报告内部请求数或重试时，不能把 Agent 活动片段数当模型调用数。TTFT、纯推理时间、浏览器可见时间与内部重试缺失时分别标记；缺失不能被吸收到一个写着“推理”的大数字里。

## 7. 主指标与继续／停止条件

| 维度 | 主指标 | 解释 |
| --- | --- | --- |
| 速度 | 到可用候选的 p50、p95；后端候选延迟、聊天完成时间作为分项 | 以任务而非 token 或工具回合作样本单位；按任务类型、缓存层分别报告 |
| 完成 | 固定预算内完成率、超时率、失败类型 | 成功样本的延迟分布旁必须显示完整分母；失败不伪装成一个“很快的完成” |
| 质量 | 保留条件、来源、几何、依赖完整性；关键遗漏数 | 运行成功、schema 合法和设计可用是不同检查 |
| 成本 | 所有尝试合计、每成功任务净成本、缓存桶及准备摊销 | 同时报告时间—成本—质量，不合成未经讨论的一个分数 |

首轮同时公布每对差值、原始散点与任务分层汇总。中位数差与“各配对差的中位数”含义不同，图表写清所用口径。后续区间估计按任务/运行块重采样，避免把同一题多次调用视为独立设计题。样本少时 p95 只是描述；若失败比例使第 95 百分位无法在期限内达到，写明“p95 未在期限内达到”，不删除失败后报一个较好的尾部值。

以下为待讨论的工程门槛，先固定后测，并非文献公认阈值：

- **停止进入产品默认：** 任一新发生的来源错误、保留条件破坏或关键依赖遗漏；先定位与修复，再使用新的预定批次复测，不以低费用抵消。
- **值得进入下一阶段：** 首轮关键错误为零，完成率不低于 A；至少在主要任务与两个缓存层中看到一致方向，并满足 p50 降低至少 15% 或每成功任务净成本降低至少 15%。若只有成本改善而时间变化不明，结论写“降成本”。小样本达到门槛只支持继续测量。
- **可考虑有限启用：** 独立任务批次重复收益；完成率差的一侧 95% 区间下界不低于 −5 个百分点，p95 比值区间上界不超过 1.10，且关键错误检查通过。数据不足以支持这些界限就保持实验选项，不宣布不劣。
- **Jev 的额外条件：** 相对于确定性 gate 的 B，含校准、Jev 调用与回退的净成本继续下降，必要干预不延迟；类型合法或 confidence 高不能替代正确率验证。

这些门槛允许“较慢但更省钱”成为一个明确权衡，也允许结果否定原先设想。若主要等待在 CAD 或前端，而非模型往返，下一步就针对对应已有 owner 做局部优化，不继续压缩模型输入。

## 8. 执行入口与本轮交付边界

已有入口可直接复用：

```powershell
# 只做离线上下文测量，不调用模型，不写设计项目。
python tools/benchmark_intent_context.py --siblings 0 100 1000 --tokenizer heuristic

# Stage 夹具与确定性预检；路径须替换为已配置实验根中的全新目录。
python tests/monkeymonitor/run_stage_handoff_benchmark.py --output <new-external-experiment-root> --prepare-only

# 读取当前路径可用的参数；help 不启动付费试验。
```
