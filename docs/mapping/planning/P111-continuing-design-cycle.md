## 四个阶段及退出条件

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| 1. 找回未完成的工作 | 核对已有 question、proposal、episode、option 的写入与恢复路径；用现有 P036 项目 run 保存仍需继续的内容，补齐现有界面的读取 | 保存一个不触发几何生成的开放问题，以及针对既定方案的拒绝理由；重启后能按同一项目和设计基准恢复，仍能定位对象与原方案 |
| 2. 让判断进入下一轮 | 复用已有 proposal / option / candidate 路径，呈现两个可比较方案；将人的解释选择、拒绝或修订意见提供给下一轮 | 人给出的理由和要求保留的条件在第二轮可见、可追溯；被拒方案仍可查看；问题可以继续开放；候选不改动正式项目位置 |
| 3. 接受并继续 | 完成 P110 前置验收；区分暂存候选、设计判断与正式发布；人的明确动作调用既有 `project.issue`，不另建 commit 机制 | 合格结果经明确动作发布后，重新打开项目能据此继续；旧基准、检查失败或阶段闭合不足时拒绝发布；人的判断、作者和理由可恢复，不能只保存在 `issue_run` 返回值中 |
| 4. 检验连续性 | 同一案例完成两轮并穿插服务重启；断开模型后读回项目并用已有确定性入口继续；用另一个不同构成的项目复核通用性 | 两个项目的恢复与后续修改成立；历史问题、方案、判断和接受记录仍可定位；记录实际返工与重复解释情况，不预设效率提升结论 |

阶段 1、2 可以先推进；阶段 3 必须等 P110 与所需 P108 行为验收。阶段 4 的断开模型检查只要求读取和已有确定性操作；更换 provider 后的生成效果在实际可用、已授权的条件下验证。

## 所有权与实施边界

实施决定为 **EXTEND**。写代码前逐项核对模块注册表的完整契约并更新对应 owner：

| 所需能力 | 现有 owner / 接口 | 本周期边界 |
| --- | --- | --- |
| 设计内容、修改、保护条件 | `state.record`、`state.operational_state`、`state.commitments` | 扩展已有表示；概念公式不变成平行 DesignState 系统 |
| 问题、提案、判断交互 | `studio.intent`，现有 proposal 与 episode 接口 | 先核对其存储实现归属；机器解释与人的判断分清来源，不把澄清响应直接当作已持久化问题 |
| 备选、比较与执行 | `studio.options`、`studio.candidate`、`studio.validation` | 复用现有候选运行、对比和对象身份 |
| 项目保存与恢复 | `project.repository`、`project.layout`、`project.record_kinds` | 沿用 P036；候选内容在所属 run，正式位置由既有项目机制维护；不增加第二个数据库 |
| 正式接受 | `project.issue`、`state.stage_workflow` | 复用发布条件和精确基准；先确定判断的既有持久化归属，再连接 UI |

如需新记录，必须指出具体缺口、唯一消费者、P036 目的地及替换的旧路径；不因愿景中出现 Questions / Uncertainty 等名词就新增机制。`module_registry.json` 描述已实现所有权，不能提前宣称本周期能力完成。

验收项目使用明确配置的外部 P036 根。运行证据按现有布局保存；提交 probe 证据时遵循已有提升流程。文档只保存计划与人读结论。
